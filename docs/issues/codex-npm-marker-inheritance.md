# inherited npm markers select the wrong codex updater

problem: account wrappers and skid provider launches preserve package-manager
provenance from their parent environment while executing the shared standalone
codex. the startup update menu can consequently select npm for a native install.
the documented maintenance command clears the markers only for that invocation.

impact: choosing update now runs `npm install -g @openai/codex`, which fails with
`EEXIST` at `~/.local/bin/codex`. the foreground agent exits with status `1`.
forcing npm to replace that symlink would change its installation owner rather
than repair native updater selection.

evidence (2026-10-11, macbook):

- the reported `0.162.0 → 0.162.1` failure used npm. the original debug log was
  read before npm inspection commands rotated it away; the pasted failure
  remains available in the investigation conversation.
- `~/.local/bin/codex` points through
  `~/.codex/packages/standalone/current` to the native `0.162.0` release. its
  executable, version output and package manifest are valid. npm's prefix is
  `~/.local`, and its global codex package is absent.
- the long-lived tmux server carries `CODEX_MANAGED_BY_NPM=1` and
  `CODEX_MANAGED_PACKAGE_ROOT=~/.local/lib/node_modules/@openai/codex`. sampled
  foreground native codex processes inherit both markers across all three
  accounts. the current personal task has the ancestry native codex → zsh →
  that server. the gateway carries neither marker and started after the server.
- the failed process has exited; its exact historical environment cannot be
  sampled. current process evidence and upstream selection logic establish
  this mechanism, but do not identify the server's original launcher.
- `~/bin/codex` and the wrapper generated by `lib/ai-tools.sh:169–179` preserve
  the markers. `assets/skid-provider/provider-command` does likewise. deployed
  skid `v0.14.0`, source `111c91b4c97e70ee154dae3032d011533951f55e`, also preserves
  them. its final shell message reports the command's failure; it does not
  choose npm.

cause: [upstream installation detection](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/install-context/src/lib.rs#L120)
treats the presence of `CODEX_MANAGED_BY_NPM` as an override before inspecting
the executable. [the update action](https://github.com/openai/codex/blob/rust-v0.162.0/codex-rs/tui/src/update_action.rs#L47)
maps that override to the reported npm command. `0.162.1` retains this detection
logic; a patch upgrade alone does not remove inherited provenance.

reproduction: inspect the selected environment of a skid foreground codex
process and its ancestors. when an update is available, launch the native cli
with the inherited npm marker and inspect the startup menu's proposed command.
do not accept the npm update against the shared native installation.

workaround: use the existing scrubbed personal installation-context command in
`docs/gateway-separation-runbook.md`, under native ai maintenance. restarting
only the gateway leaves the existing tmux server's environment intact.

follow-up: follow [the local implementation plan](../codex-native-launch-plan.md).
remove stale package-manager provenance at all four owned native invocation
sites: account wrappers, scoped provider commands, version inspection and the
memory configuration writer. preserve literal arguments, account selection,
existing sessions and upstream installation ownership. do not parse updater
arguments or force every account to use the personal `CODEX_HOME`.

resolved when: native launches from an npm-marked parent no longer select npm;
the personal startup menu selects the native updater; account homes and literal
argument forwarding remain correct; and the documented maintenance command
still updates the shared installation. work-account installation discovery is
a separate upstream limitation: its selected `CODEX_HOME` does not contain the
shared release, so marker removal alone does not make work-account self-update
discover that installation.
